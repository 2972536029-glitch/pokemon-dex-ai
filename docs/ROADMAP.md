# 宝可梦图鉴 AI 版 · 产品路线图与设计决策

> 状态:设计定稿,未开工(2026-09-20 与余尧讨论沉淀)
> 原则:**先部署,后迭代**——Phase 0 完成前,任何新功能不插队。
> 面试讲解手册(当前 AI 问答的实现 why)在 `../server/README.md`;本文档只管未来。

## 0. 愿景与主线守恒

从"图鉴问答助手"演进为 **AI 驱动的宝可梦卡牌平台**:问答(已上线)、推荐、推演三类 AI 能力,
资产、抽卡、对战三段游戏循环。

**主线守恒原则**:简历与面试的标题级卖点永远是 AI(Agent 循环 / 工具编排 / 幻觉校验),
游戏功能是 AI 的"应用土壤"。实现任何一期时,先问"这一期的 AI 增量是什么"——
卡包系统本身是常规工程,不构成卖点;AI 基于用户资产的策略能力才是。

## 1. 游戏闭环(产品骨架)

```
每日登录 / 对战胜  →  赚应用内货币  →  抽卡包  →  收藏增值
        ▲                                        │
        └────── 对战胜(用收藏的卡组队出战)←── AI 组队推荐
```

- **账号是资产锚点**:钱包、卡牌收藏、对战战绩全部挂在账号名下——没有账号,闭环每一环都不成立
- 货币只有应用内一种,**永不做真实支付**
- 抽卡概率**公开公示**在卡包页面上(合规习惯 + 工程诚实)

## 2. 分期路线

### Phase 0 · 部署当前 AI 问答版【下一步,最高优先级】
- 内容:push `feat/ai-chat` → MR → 合并 → 部署上线(见 server/README.md 部署节)
- 验收:线上可演示,简历标题补「已上线」,重建 all
- 备注:此步之前不动任何新功能

### Phase 1 · 账号 + 钱包 + 卡包收藏 + AI 推荐顾问
数据与它的 AI 层**一起交付**,不做裸登录、不做没有 AI 的卡包。

- 范围:注册/登录、钱包(应用内货币)、卡包(3~4 个主题包 + 公示概率)、抽卡入库、
  **AI 组队推荐**(基于我的收藏)、**AI 卡包推荐**(基于收藏缺口 + 钱包 + 概率)
- 数据模型:
  - `cards` 静态卡目录(PokeAPI 数据 + 稀有度 + 卡面),全局一份
  - `user_cards` 持有关系(谁、哪张、几张、来源);目录与持有分离,逻辑外键
  - `wallet` / `wallet_tx` 货币与流水;`packs` 卡包定义与概率表
  - **抽卡 = 一张订单**:扣货币 → 随机产出 → 入库,同一事务;连点防重用幂等键;
    余额扣减 `UPDATE ... WHERE balance >= ?` + RowsAffected 判定(乐观锁,复用课程知识)
- 登录方案:httpOnly Cookie + 服务端 Session(抗 XSS,**不用** localStorage 存 JWT);
  密码 argon2/bcrypt;登录限流;错误信息统一"用户名或密码错误"(防用户枚举)
- 存储:SQLite v1(仓储层隔离,后续可换 MySQL);注意 PaaS 免费档文件系统临时,SQLite 须挂卷
- AI 工具层质变:新增**用户状态工具**(`查我的收藏` / `查我的钱包` / `查卡包列表`)。
  安全红线:**用户身份由服务端从会话注入工具,绝不允许模型传用户 ID**——工具层越权(IDOR)防御
- 幻觉校验器扩展:组队/卡包推荐是可机械核对的断言——
  推荐的宝可梦必须 ∈ 用户收藏;引用的卡包名/价格/概率必须与定义一致
- 推荐伦理(产品纪律,写死):每条推荐必须引用数据依据(缺口/内容/概率/价格);
  禁止话术;**AI 必须会说"别买"**(钱包不足或收藏不缺时明确说价值低)——
  可信推荐 > 转化率导向,这是 AI 伦理落地到产品的具体答案
- 验收:能注册→抽卡→让 AI 按我的收藏组队并核对每张卡确实拥有;推荐理由全部引用真实数据

### Phase 2 · AI 对战模拟
- 范围:从收藏选 3 张组队 → 与 AI 对手回合制对战,模型基于真实种族值 + 属性克制倍数推演
  (伤害计算、先手顺序),每步引用工具数据、可被校验器核对;战胜得货币
- 设计红线:**不做养成系统、不做自定义数值平衡**——强度即真实种族值,稀有度只影响卡面与抽中概率
- AI 增量:多轮状态推演(战斗状态作为工具可查的上下文),复用现有 Agent 循环
- 验收:一局完整对战可回放,每回合的伤害/克制结论能对照图鉴数据核验

### Phase 3 · 真人对战 PvP【可选,最后】
- WebSocket 实时对战、匹配、服务器权威状态机——量级完全不同,只在想讲"实时系统"故事时启动
- 启动前置:Phase 0-2 全部上线且有真实使用

## 3. 跨期的工程约定

- 技术栈不混用:前端保持 JSX + React 19;服务端 TypeScript + Express;新增持久层 SQLite
- 每期上线走同一流程:本地 commit → diff review(余尧)→ push/MR → 导师 Code Review → 部署
- 幻觉校验器随功能扩张:数值断言(已有)→ 类型断言(已有)→ 用户状态断言(Phase 1)
  → 战斗推演断言(Phase 2);宁漏判不误判的原则不变
- AI 叙事对应简历:Phase 0 锁定现有内容;Phase 1 加"鉴权工具执行/用户状态校验";
  Phase 2 加"多轮战斗推演"——每次迭代后过一遍 content.json,真实可讲才写

## 4. 明确不做(防蔓延)

- 真实支付 / 充值
- 卡牌养成、强化、交易行(经济平衡是无底洞)
- 自定义宝可梦数值
- 任何"限时/稀有/速来"式话术
