# 更新计划 · v1.2 AI 对战模拟(Phase 2)

> 状态:设计定稿,未开工。本文档是 v1.2 的施工图,实现时逐节对照。
> 上游:产品报告书 docs/PRODUCT.md · 路线图 docs/ROADMAP.md · 上线版本 v1.1(commit 395bcf5)

## 一、这个更新解决什么

v1.1 的闭环是"赚币 → 抽卡 → 收藏",但**收藏没有用途**。v1.2 给卡牌一个使用场景:
用你收藏的卡组队,和 AI 对手打回合制对战,赢了赚货币——闭环转起来。

AI 叙事升级:AI 从"问答/推荐"进化为"**对战推演**"——模型基于真实种族值与属性克制
做多轮决策,每一步可被守卫核对。

## 二、核心设计决策(先定原则,再写代码)

### 决策 1:伤害由服务器计算,模型只"选择行动"

AI 的职责是**决策**(用哪只、放哪个技能),不是**算数**。伤害公式在服务端以纯函数实现:

```
伤害 = ((2×等级/5 + 2) × 威力 × 攻/防) / 50 + 2,再乘属性克制倍数与随机数(0.85~1.0)
```

- 克制倍数来自已入库的属性克制表(不是让模型背)
- 先手顺序按速度值
- 为什么这么定:模型算数会错(幻觉),服务器算数是确定性的——**把模型放在它擅长的
  决策层,把计算放在确定性层**。这是本产品一以贯之的架构哲学(问答查工具、战斗算引擎)

### 决策 2:战斗状态是"服务器权威"的单一事实源

`battles` 表存完整战斗状态(双方阵容/HP/回合数/日志),每次行动后由服务器更新并返回
快照。前端与模型都只是状态的"读者"。刷新页面不丢战斗;断线重连可恢复。

### 决策 3:AI 对手 = 同一个 Agent 循环,不同系统提示

不复用规则脚本,也不上强化学习——AI 对手就是现有 Agent 循环 + 对战系统提示词 +
战斗状态工具。它的每次选择(出哪只/放什么招)都要引用工具返回的真实数据,幻觉守卫
照样核对(比如它声称"克制"但数据不支持 → 检出并纠错)。

## 三、数据模型(新增表)

```sql
CREATE TABLE battles (
  id           TEXT PRIMARY KEY,            -- battle_<random>
  user_id      BIGINT NOT NULL REFERENCES users(id),
  user_team    JSONB NOT NULL,              -- [{card_id, hp, max_hp}] 出战 3 只
  ai_team      JSONB NOT NULL,
  active_user  INTEGER,                     -- 场上位置
  active_ai    INTEGER,
  turn         INTEGER NOT NULL DEFAULT 1,
  status       TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','won','lost')),
  log          JSONB NOT NULL DEFAULT '[]', -- 每回合 {turn, actor, action, dmg, text}
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at  TIMESTAMPTZ
);

ALTER TABLE users ADD COLUMN IF NOT EXISTS last_battle_at TIMESTAMPTZ; -- 对战冷却/奖励用
```

奖励:胜利 +100(写 wallet_tx kind='battle',量入为出防通胀:每日首胜双倍,后续减半——实现时定)。

## 四、API 设计

| 路由 | 方法 | 说明 |
|---|---|---|
| /api/battle/team | POST | 保存出战阵容({cardIds: [3 只]}) |
| /api/battle/start | POST | 创建战斗,返回初始状态(服务器按收藏生成 AI 对手阵容) |
| /api/battle/:id/state | GET | 当前状态快照 |
| /api/battle/:id/turn | POST | 用户行动 {action: "move", moveId} → 服务器结算双方行动 → 返回回合日志 |
| /api/battle/:id/forfeit | POST | 投降 |

结算流程(单事务):用户行动 → 检查 KO → AI 行动(AI 策略见下)→ 检查 KO → 回合数+1 →
写日志 → 若结束则发奖励 + 写 wallet_tx。

## 五、AI 对手的两种模式(产品差异点)

| 模式 | 实现 | 价值 |
|---|---|---|
| 规则模式(默认,零成本) | 服务端确定性策略:优先克制倍数高的招,HP 低时换人 | 永远可用,不烧 token |
| AI 推演模式(演示用,✅ 已上线 v1.2.x) | 战斗状态+预计算克制数据喂给模型,模型选择行动并**说明理由**,行动经合法性校验、理由经守卫与实际倍数核对(不符标注警示),任何失败回退规则模式 | 面试演示:实测中守卫曾当场标注模型谎称"克制"(实际 1x) |

开关放在创建战斗时选择,两种模式写同一张 battles 表。

## 六、幻觉守卫扩展(战斗版)

- 结算文本中的克制断言:已由现有 checkTypeClaim 覆盖(数据源换成战斗引擎的克制表)
- AI 推演模式下,模型声明的伤害/剩余 HP 与服务器计算值逐一核对 → 不符走既有
  "纠错一次 → 可见警示"流程
- 回合日志本身是结构化数据,前端直接渲染,不经过模型转述——**从根上消灭转述失真**

## 七、前端设计

- 收藏页新增"编队"入口:从收藏中选 3 只(已选高亮)
- 战斗页:双方卡牌 + HP 条 + 回合日志流 + 行动按钮(招式来自该卡的属性,招式威力表内置)
- 结算页:胜/负 + 奖励入账提示 + "查看战斗日志"
- 全部走既有 hash 路由与主题变量,无新依赖

## 八、验收清单(实现时逐条对照,QA 按此验收)

- [ ] 组队:只能选收藏中的卡;未组队无法开战
- [ ] 伤害:同一输入多次结算,数值确定性一致(随机数种子可控);克制倍数与属性表一致
- [ ] 先手:速度高者先动;速度相同随机
- [ ] KO:HP 归零强制换人;无可换 → 战斗结束 → 奖励入账有流水
- [ ] AI 规则模式:不调模型、零 token 消耗、行为可预测
- [ ] AI 推演模式:理由引用真实数据;守卫核对失败有可见警示
- [ ] 断线恢复:刷新/重开浏览器后战斗状态不丢
- [ ] 越权:不能操作别人的战斗;不能提交非法行动(未上场/已 KO)
- [ ] 回归:qa/e2e.mjs 原 18 断言全过 + 新增战斗断言

## 附:实现偏差记录(2026-09-24,QA 第三轮后补)

- battles 表实现为单 `state JSONB` 快照(设计稿的多列拆分在 JSONB 下冗余),状态/回合仍单独建列供索引与乐观锁
- AI 对手不再向模型"声明伤害/HP"——伤害全部由服务器引擎计算,模型只声明行动与理由;因此 §六 的"伤害声明核对"演化为"理由与行动配对 + 克制断言守卫"(checkTeamRecommendations 同源)
- 非法行动(不存在的招式)按设计回退普招而非拒绝:前端只展示合法招式,接口层的静默回退是纵深防御;QA V12 已固化为断言
- 伤害公式中等级固定 50、随机数区间 0.85~1.0,与主线作品保持可解释性优先
