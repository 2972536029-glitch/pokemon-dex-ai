# v2.2 好友系统计划书 —— 双向同意 · 赠送/索要 · 好友对战

> 需求(用户 2026-10-07):①好友申请,双方同意才能成为好友(不是单向关注);②好友可赠送自己不需要的宝可梦;③赠送 + 索要双向系统;④好友之间可申请对战。
> 本文档是工作留痕的起点:先立项评审,再分三期实施,每期独立 commit。

## 1. 目标与范围

| 能力 | 说明 |
|:--|:--|
| 好友关系 | 按用户名发起申请 → 对方同意 → 成为好友;可拒绝、可删除好友;上限 50 人 |
| 赠送/索要 | 好友之间发起「我送你某卡」或「我向你要某卡」,对方同意才成交,事务保证一手交一手 |
| 好友对战 | 异步 PvP:挑战者携编队下战书 → 对方接受并选编队 → 服务端一次性模拟整场 → 双方看同一场战报,胜者有奖 |

**非目标(明确不做,防止范围膨胀)**:实时 WebSocket 对战/聊天(Vercel serverless 无长连接);全局交易市场(只限好友);段位天梯(Phase 3 可选);离线消息推送。

## 2. 数据模型(DDL 内嵌 schema.ts,幂等迁移)

沿用项目工程约定:**不用物理外键,引用完整性由应用层+事务保证;状态字段用 SMALLINT + 应用层常量映射**(可扩展,改代码不改表)。

```sql
CREATE TABLE IF NOT EXISTS friend_requests (
  id BIGSERIAL PRIMARY KEY,
  from_uid INTEGER NOT NULL,
  to_uid   INTEGER NOT NULL,
  status   SMALLINT NOT NULL DEFAULT 1,   -- 1 待处理 2 已同意 3 已拒绝
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  handled_at TIMESTAMPTZ
);
-- 同一方向只允许一条待处理申请(部分唯一索引,天然防重复骚扰)
CREATE UNIQUE INDEX IF NOT EXISTS uq_friend_req_pending
  ON friend_requests (from_uid, to_uid) WHERE status = 1;
CREATE INDEX IF NOT EXISTS idx_friend_req_inbox ON friend_requests (to_uid, status);

CREATE TABLE IF NOT EXISTS friendships (
  id BIGSERIAL PRIMARY KEY,
  user_a INTEGER NOT NULL,               -- 恒为较小 uid,防双向重复建交
  user_b INTEGER NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT uq_friendship_pair UNIQUE (user_a, user_b)
);

CREATE TABLE IF NOT EXISTS card_trades (
  id BIGSERIAL PRIMARY KEY,
  kind     SMALLINT NOT NULL,            -- 1 赠送(我送你) 2 索要(你给我)
  from_uid INTEGER NOT NULL,             -- 发起人
  to_uid   INTEGER NOT NULL,             -- 接收人/被索要人
  card_id  INTEGER NOT NULL,
  status   SMALLINT NOT NULL DEFAULT 1,  -- 1 待处理 2 已成交 3 已拒绝 4 已撤销
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  handled_at TIMESTAMPTZ
);
CREATE INDEX IF NOT EXISTS idx_trades_inbox ON card_trades (to_uid, status);

CREATE TABLE IF NOT EXISTS friend_battles (
  id BIGSERIAL PRIMARY KEY,
  challenger_uid INTEGER NOT NULL,
  target_uid     INTEGER NOT NULL,
  challenger_team JSONB NOT NULL,        -- [cardId×3] 下战书时的编队快照
  target_team    JSONB,                  -- 接受时才填
  status  SMALLINT NOT NULL DEFAULT 1,   -- 1 待应战 2 已完赛 3 已拒绝 4 已撤销
  winner_uid INTEGER,
  battle_log JSONB,                      -- 完整回合战报
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at TIMESTAMPTZ
);
CREATE INDEX IF NOT EXISTS idx_fbattles_inbox ON friend_battles (target_uid, status);
```

## 3. 关键规则设计(工程取舍点)

1. **双向同意,一处小体贴**:A 向 B 发申请时,若 B 恰好也正向 A 发过待处理申请,直接视为双方同意,一步建交(顺带把两条 pending 一并关掉)——这是微信式"互加秒通过"。
2. **赠送保护出战编队**:允许赠送持有 count≥2 的重复卡一键成交;**唯一一张的卡默认也可送,但若它在你的出战编队里会被拒**(提示先换下编队),避免送掉后编队变废。索要同理只校验被索要方。
3. **成交必须是事务**:扣减方 `UPDATE user_cards SET count=count-1 WHERE user_id=$1 AND card_id=$2 AND count>=1` 行数=0 即回滚报"卡已不在",接收方 upsert +1;**成交瞬间重校验双方仍是好友**(防先加好友→撤销好友→成交套利)。
4. **防刷上限**:待处理单向申请同向仅 1 条(索引兜底);单人挂起 trade ≤ 10;好友战奖励每账号每天最多结算 10 场(应用层 count 查询,不加表);不能对自己发起任何请求。
5. **异步对战模型**(不用 WebSocket 的原因:Vercel serverless 无长连接):战书快照挑战者编队 → 被挑战者接受时选编队 → 服务端用现有引擎(`battleMonFromCard` + `resolveTurn` + `seededRng(战书id)`)一次模拟整场,战报 JSONB 落库,双方拉取同一份,不可篡改;被赠送/赠掉导致卡片变动在**接受时**统一重校验持有。
6. **奖励**:胜 +100 / 负 +20 / 平 +50,走 `wallet_tx kind='battle'`(**CHECK 约束已允许,不碰 DDL 枚举**——QA-033 的教训);每天最多 10 场计入奖励,超出只出战报不加币。

## 4. API(全部登录态,新增 routes-friends.ts)

| 方法/路径 | 作用 |
|:--|:--|
| POST `/api/friends/request` {username} | 发好友申请(互发自动通过) |
| GET `/api/friends` | 好友列表 + 收到的申请 + 发出的申请 + 挂起 trade/战书计数(一次拉全,供红点) |
| POST `/api/friends/requests/:id/accept` · `/decline` | 同意/拒绝 |
| DELETE `/api/friends/:uid` | 删除好友(双向消失,挂起交易自动拒绝) |
| POST `/api/friends/:uid/trades` {kind, cardId} | 发起赠送/索要 |
| GET `/api/friends/trades` | 收到的/发出的 trade 列表(含双方持有份数快照) |
| POST `/api/trades/:id/accept` · `/decline` · `/cancel` | 处理;accept 走事务交割 |
| POST `/api/friends/:uid/challenge` {cardIds×3} | 下战书 |
| POST `/api/friend-battles/:id/accept` {cardIds×3} · `/decline` · `/cancel` | 应战即模拟,返回战报 |
| GET `/api/friend-battles/:id` | 战报回看(双方皆可) |
